| 14 | **Field incident, recorded for the audit**: the phase-3 work OOM-killed the operator's tmux window twice | `Command::output()` buffers a child's whole output, so a test running `yes` reached a 60 GB resident set; the kernel log names `agentd_agent-c5` five times at 21:30 and a `bash` in a `tmux-spawn` scope at 21:53, each near 60 GB. | 15 | **Widen the `Capability` seam before writing the model capability**, in the same PR | `OutputKind::Progress` existed but `act` returned exactly one output, so a capability that runs for minutes could not report while it worked, though `docs/session/agent.md` says the agent publishes its progress. | 17 | The first provider is an **OpenAI-compatible `chat/completions` endpoint** | The operator chose it on 2026-09-29, when the loop-first order left the provider open. The loop is written against the shapes that protocol needs — role-tagged messages, tool calls carrying ids, results paired by id — while the seam stays the agent's own types, so the client owns the wire format and a provider's shape does not become the agent's contract. The client itself is the next unit and has not landed | this row; `agentd/src/model.rs`; `docs/session/agent.md` | done (decided) |
| 18 | **Nothing crosses into the model's context unbounded** | The `shell` capability caps a command at a mebibyte, which is right for the log and far too much for a model: a few turns would fill any context window. Each stream is cut to 8 KiB separately, so neither can crowd the other out of the model's view, and the whole result is cut again, so an unknown tool's detail shape is bounded too. The turn count is bounded as well (32), so a model that never stops calling tools cannot hold the session. A model's context is a resource like any other, and this is the same rule that followed the OOM incident above | `agentd/src/task.rs`; `MAX_TOOL_RESULT_BYTES`, `MAX_TOOL_MESSAGE_BYTES`, `MAX_TURNS` | done |
| 19 | The session's egress allowlist is **derived** from each declared endpoint's `base_url` | The operator asked for the OpenAI-compatible endpoint's allowlist to come from a settings file. A host list declared beside the endpoint can name a host the endpoint does not use, or miss the one it does, and the session then reaches nothing while the file looks right; deriving the rule from the URL makes that drift impossible. The derived rule is a destination with its port, so `AgentImage` carries `HostPort` rules rather than host names, and an endpoint on a non-default port becomes a rule of its own | `daemon/src/settings.rs`; `daemon/src/image.rs`; `daemon/src/egress.rs`, where the test-only `start_with_rules` seam is gone because the image can name a port; this row | done |
| 20 | The file is `$XDG_CONFIG_HOME/agent/config.toml`, falling back to `$HOME/.config/agent/config.toml`, and it is the **only** scope | The operator referenced the settings document (`docs.x.ai/build/settings`) and chose the XDG location. That document's managed, requirements, and project scopes exist for deployments this project has none of, and a project-scope file would let a repository grant its own agent egress, which the trust rule already refuses a binary inside a write root for. An absent file is an empty set, which grants no egress, the same fail-closed default an empty allowlist has | `daemon/src/settings.rs::config_path`; this row | done |
| 21 | Only `https` endpoints are accepted; a plaintext one is refused when the file is read | The egress proxy speaks `CONNECT` only and the sandbox gives the command no route but that proxy, so an `http` endpoint cannot be reached at all. | 22 | `config_path` takes the two directories as arguments; the library never reads the environment | Setting an environment variable from a test is `unsafe` in edition 2024, which this workspace denies everywhere, so a library that read `XDG_CONFIG_HOME` itself could not be driven by a test and its mutants would be missed.
